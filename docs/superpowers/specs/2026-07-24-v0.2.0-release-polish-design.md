# GitHub Repo Doctor v0.2.0 Release Polish Design

**Date:** 2026-07-24
**Status:** Approved for implementation planning

## Summary

GitHub Repo Doctor already has a complete local-scanner MVP, versioned configuration,
192 passing tests, warning-free distributions, and a public `main` branch at
`https://github.com/3xpp/RepoDoctor`. This milestone makes that existing `0.2.0`
release credible as a polished public pre-release without changing scanner behavior,
scoring, dependencies, report semantics, or package version.

The milestone adds continuous integration, repository and package metadata,
contributor-facing community files, GitHub issue and pull-request templates, curated
repository settings, private vulnerability reporting, and a tagged GitHub
pre-release with freshly built source and wheel archives.

Phase 2 scanner checks remain a separate `0.3.0` design and implementation cycle.

## Goals

- Run the complete supported quality contract automatically on pushes and pull
  requests.
- Present accurate project, license, Python, CI, and release metadata to visitors.
- Give contributors deterministic setup, testing, issue, and pull-request guidance.
- Provide a private security-reporting route without publishing personal contact
  details.
- Configure the public repository for a solo maintainer without imposing pull-request
  or branch-protection requirements.
- Publish the current code and repository polish as an annotated `v0.2.0` Git tag and
  GitHub pre-release.
- Preserve local/remote commit parity, a clean worktree, and immutable published
  history.

## Non-goals

- No Dockerfile is added merely to improve the repository score.
- No PyPI publication occurs in this milestone.
- No remote repository scanning, GitHub API integration in the product,
  authentication, AI, web application, or SaaS behavior is added.
- No scanner check, finding, severity, score, configuration rule, report field, or
  runtime dependency changes.
- No `0.3.0` community-health scanner checks are implemented.
- No mandatory pull requests, branch protection, CODEOWNERS, Dependabot, or other
  team-governance automation is enabled.

## Repository Content

### Continuous integration

Create `.github/workflows/ci.yml` with workflow name `CI`.

Triggers:

- pushes to `main`;
- all pull requests;
- manual `workflow_dispatch`.

Safety and concurrency:

- default permissions are `contents: read`;
- superseded runs for the same workflow/ref are cancelled;
- third-party and GitHub-authored actions use immutable commit SHAs, with comments
  recording their verified release versions;
- implementation verifies current action releases from official upstream sources
  before selecting those SHAs.

Jobs:

1. `tests` uses a Python matrix of `3.12`, `3.13`, and `3.14`. Each matrix entry
   checks out the repository, installs the matching Python through the uv setup
   action, runs `uv sync --locked`, then runs unit and end-to-end tests.
2. `quality` uses Python `3.12`, runs `uv sync --locked`, Ruff lint, Ruff formatting
   in check mode, strict mypy, the distribution build, and
   `repo-doctor scan . --fail-under 90`.

The workflow file itself makes the root CI check pass, so the repository's
deterministic score becomes `95/100`; missing Docker support remains the only
intentional finding.

### Package and README metadata

Add a `[project.urls]` table to `pyproject.toml`:

- `Homepage`: `https://github.com/3xpp/RepoDoctor`
- `Repository`: `https://github.com/3xpp/RepoDoctor`
- `Issues`: `https://github.com/3xpp/RepoDoctor/issues`
- `Security`: `https://github.com/3xpp/RepoDoctor/security/policy`

Add README badges for:

- the `CI` workflow;
- Python `>=3.12`;
- MIT license;
- the latest GitHub release including pre-releases.

README community links point to the tracked contribution, security, conduct, issue,
and pull-request guidance. Installation text remains honest: the project is not
published to PyPI, so the existing local/source installation methods remain
authoritative.

### Community health files

Create:

- `CONTRIBUTING.md`
- `SECURITY.md`
- `CODE_OF_CONDUCT.md`
- `.github/ISSUE_TEMPLATE/bug-report.yml`
- `.github/ISSUE_TEMPLATE/feature-request.yml`
- `.github/ISSUE_TEMPLATE/config.yml`
- `.github/pull_request_template.md`

`CONTRIBUTING.md` documents Python 3.12+, uv setup, focused and complete validation,
fixture expectations, conventional commits, deterministic behavior, documentation
updates, and secret-safety requirements.

`SECURITY.md` states that the latest `0.2.x` pre-release is supported, directs
reports to GitHub private vulnerability reporting, asks reporters not to open public
issues or include live credentials, and avoids publishing a personal email address.

`CODE_OF_CONDUCT.md` provides a concise project-specific conduct and enforcement
policy. Conduct concerns are reported privately through the contact route on the
maintainer's GitHub profile rather than through a public issue. Security advisories
are not repurposed for conduct reports.

The bug form requests version, Python version, operating system, reproduction,
expected and actual behavior, and sanitized logs. The feature form requests problem,
proposal, alternatives, and local-only scope impact. Blank issues are disabled, and
the issue-template configuration links security reporters directly to the private
advisory form. The pull-request template checks tests, documentation, stable JSON and
scoring implications, conventional commits, and secret safety.

### Durable maintainer guidance

Update `AGENTS.md` so future sessions:

- keep CI action references immutable and reviewed;
- run the full release gates before tagging;
- never create or move a published release tag to bypass a failed release;
- keep community guidance synchronized with actual commands.

Append one dated decision to `docs/DECISIONS.md` describing the solo-maintainer CI and
pre-release policy. Modify `docs/FAILURES.md` only if implementation encounters a
genuinely new failure not already covered by its existing sandbox or patch-helper
entries.

## GitHub Repository Settings

The repository remains public with `main` as its default branch.

Set:

- description: `A deterministic Python CLI that scores repository readiness and recommends practical fixes.`
- topics: `python`, `cli`, `github`, `open-source`, `repository-health`,
  `developer-tools`, and `code-quality`;
- Issues: enabled;
- Wiki: disabled;
- private vulnerability reporting: enabled.

Direct pushes remain allowed. Branch protection, mandatory pull requests, Discussions,
Projects, and a repository homepage URL are not added in this milestone.

Every setting change is read back through GitHub CLI/API output after mutation.

## Release Flow

Release publication is deliberately ordered:

1. Add and validate repository content locally.
2. Commit the work in small conventional commits.
3. Run unit tests, end-to-end tests, aggregate pytest, Ruff lint, Ruff formatting
   check, strict mypy, the build, fixture scans, JSON parsing, `--fail-under`, and a
   root self-scan.
4. Push `main` and verify local `HEAD`, `origin/main`, and remote `main` match.
5. Apply and read back the approved GitHub repository settings.
6. Wait for the pushed `CI` workflow to complete successfully.
7. Build `github_repo_doctor-0.2.0.tar.gz` and
   `github_repo_doctor-0.2.0-py3-none-any.whl` into a fresh temporary release
   directory and audit their manifests and metadata.
8. Create annotated tag `v0.2.0` at the verified release commit with message
   `GitHub Repo Doctor v0.2.0`, then push that tag.
9. Publish GitHub release `GitHub Repo Doctor v0.2.0` as a pre-release with curated
   highlights, source-install instructions, validation evidence, known limitations,
   and both distribution archives attached.
10. Read back the release URL, pre-release state, tag SHA, and asset names.

The release is not marked as the latest stable release and is not uploaded to PyPI.

## Failure Handling

- Any local quality-gate failure blocks commits and publication until a tested fix is
  committed.
- Any GitHub CI failure blocks tag and release creation.
- A tag is never created before the release commit and CI result are verified.
- If GitHub release creation fails after the valid tag is pushed, preserve the tag
  and retry release creation. Do not delete, force-move, or rewrite the tag.
- If a repository setting cannot be applied, report the exact setting and leave all
  successfully verified settings unchanged unless a safe correction is clear.
- Temporary release artifacts are created outside the repository and removed only
  after the published asset audit succeeds.
- No `.env`, credential file, key, token value, or process secret is read or copied
  during validation or publication.

## Validation and Acceptance

Local acceptance requires:

- `make install`
- `make test`
- `make test-e2e`
- `make lint`
- `uv run ruff format --check .`
- `make typecheck`
- `make build`
- `uv run pytest`
- root terminal and JSON scans at `95/100`, with six of seven checks passing and only
  Docker missing;
- good fixture at `100/100`;
- bad fixture at `25/100`;
- bad fixture with `--fail-under 80` exiting exactly `1`;
- valid JSON output and unchanged report field order/version `0.2.0`;
- package metadata containing only Pydantic, Rich, and Typer runtime dependencies;
- no scanner, scoring, model, configuration, or dependency diff;
- `git diff --check` and a clean worktree.

Remote acceptance requires:

- `main` synchronized locally and remotely;
- `CI` completed successfully for the release commit;
- description, topics, Issues, Wiki, and private reporting read back as designed;
- annotated `v0.2.0` resolving to the release commit locally and remotely;
- GitHub release marked as a pre-release with both audited archives;
- no uncommitted changes and no push beyond the explicitly approved repository.
